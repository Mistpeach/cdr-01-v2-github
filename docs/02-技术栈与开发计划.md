## 1. 目标与范围

### 1.1 目标

| 编号 | 目标 | 说明 |
| --- | --- | --- |
| G1 | 单 BLE 连接 | 上位机与下位机只建立一个 BLE 连接；左右两侧的指令在同一通道内多路复用（帧内带侧标识） |
| G2 | 左右独立 6 通道 | 左侧 L0-L2（GPIO4/5/15）、右侧 R0-R2（GPIO16/17/18），两侧状态完全独立 |
| G3 | 轨迹与原版一致 | 运动引擎（IK/FK、插值、Approach、REPEAT、轨迹曲线、随机动作、T-Code Live）照搬原作者实现，逐条复刻 |
| G4 | 兼容原作者 CSV | 上位机能直接播放原作者格式脚本：`时间ms,左命令,右命令`（无表头、RFC4180、左/右列分别发往对应侧） |
| G5 | 全新通讯协议 | 不兼容原版 `CDR01` GATT 服务与文本协议；新协议自带帧校验与状态回传 |
| G6 | 可调试可排障 | USB 串口保留独立调试通道（文本命令 + 日志） |

### 1.2 明确不做（v1.0 范围外）

- ❌ 兼容原作者四款上位机（旧 App 连不上 v2 固件是预期行为）。
- ❌ 手机 App/PWA——技术栈上留扩展位，但不进 v1.0 排期。
- ❌ 电池充电管理（沿用现有固定值/ADC 方案）。
- ❌ 多台 v2 设备同时连一台上位机——协议设计留扩展位（连接管理对象化），v1.0 只支持 1 对 1。

> ✅ 视频同步**纳入 v1.0 核心**（2026-xx 决策）：上位机仿 cdr-player，用 mpv 播放视频/音频，
> 与 CSV 脚本时间轴同步（见 §2.2、§5）。

## 2. 软件技术栈（推荐方案）

### 2.1 下位机（固件）

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 构建 | **PlatformIO + espressif32@6.9.0（Arduino core 3.0.7）** | 与现有验证环境一致；已在本机编译通过，无新增依赖 |
| 运动引擎 | **复用 v1 已移植的 `DeltaRobot ×2` + `DeltaCommandParser`** | 照搬原作者的运动控制与命令解析，轨迹一致性由"同一份代码"保证 |
| 舵机 HAL | **ServoHAL（LEDC 6 路，50Hz/14bit）** | 不变 |
| BLE 栈 | ESP32 core 自带 Bluedroid BLE | 支持 write/notify、多连接、MTU 交换；API 已在 v1 验证 |
| 串口 | USB-CDC 115200（调试通道） | 不变 |
| 新增 | `V2Protocol` 帧编解码模块（CRC16）+ `V2Transport`（BLE 收发） | 全新通讯层，与运动引擎解耦 |

### 2.2 上位机（推荐：Python 桌面 GUI）

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 语言 | **Python 3.11+** | 你机器上原作者工具全是 Python 生态；开发迭代最快 |
| BLE | **bleak ≥0.22** | 跨平台 BLE 客户端事实标准；支持 Win10/11、异步 API、MTU 协商、写/通知回调 |
| GUI | **PySide6** | 桌面原生控件、表格/滑块/日志一应俱全；比 customtkinter 更适合做时间轴/日志面板 |
| 视频/音频 | **mpv（python-mpv）+ 随包内置 libmpv** | 仿照 cdr-player 的媒体同步路径；libmpv 直接 vendor 进发布包，用户无需装 mpv |
| 打包 | **PyInstaller**（单 exe，含 libmpv） | 交付友好，`--onefile --windowed`（libmpv 作为附加数据文件） |
| 结构 | 单包多模块：`ble/ protocol/ csv/ player/ ui/` | 逻辑与 UI 分离，协议层可单测 |

**备选对比**（供参考，不采用）：

| 备选 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| Web PWA（Web Bluetooth） | 手机可用、免安装 | Windows 仅 Chrome/Edge 支持；后台定时器精度差，脚本密集段易抖动 | v2.0 可做手机版 |
| C#/WPF | 原生 Windows、BLE API 成熟 | 开发慢、你的环境无 .NET 工具链积累 | 不采用 |
| Rust/Tauri | 体积小 | 生态/迭代速度不适合本项目 | 不采用 |

## 3. 新通信协议设计（初稿，P1 前冻结）

### 3.1 GATT 布局（一条 BLE 连接）

| 项 | 值 | 说明 |
| --- | --- | --- |
| 广播名 | `CDR01v2` | 与旧版 `CDR01` 区分，避免混连 |
| Service UUID | `b4a00001-0000-4f00-9c1d-cdr01v2xxxx`（P1 生成随机 UUID，v2 专用） | 全新，不复用原版 UUID |
| **CMD** 特征（写） | Write + Write Without Response | 上位机 → 下位机命令帧（单连接内左右复用） |
| **EVT** 特征（通知） | Notify + Read | 下位机 → 上位机：命令响应（OK/ERR）、状态事件；Read 返回最近一条事件文本 |
| 电池服务 | 0x180F / 0x2A19（可选保留） | 上位机显示电量；不参与控制 |

连接策略：上位机**按广播名精确匹配 `CDR01v2`** 扫描连接；断线自动重连（指数退避 1s→2s→4s…上限 10s）；MTU 请求 ≥247。

### 3.2 命令帧（CMD，上位机 → 下位机）

```
偏移  0     1     2     3     4      5 .. 4+N-1   4+N .. 4+N+1
     0xCD  0x01  SIDE  LEN_LO LEN_HI  payload[N]  CRC16(CCITT-FALSE)
```

| 字段 | 值 | 说明 |
| --- | --- | --- |
| magic | `0xCD 0x01` | 帧头；串口调试通道不受此协议约束 |
| SIDE | `0x00`=双侧镜像；`0x01`=左侧；`0x02`=右侧 | 替代 v1 的 `L:`/`R:` 文本前缀，左右复用在一条连接上 |
| LEN | 2 字节小端，1..240 | payload 长度 |
| payload | **原作者的 ASCII 命令文本** | `POINT 0 0 0 300`、`REPEAT_LINE ...`、`STOP`、`VIBRATE 50` 等，命令集与 v1 完全一致（照搬 `DeltaCommandParser`），不含侧前缀 |
| CRC16 | CCITT-FALSE，覆盖 SIDE+LEN+payload | 校验失败：丢弃 + 回 `ERR CRC` |

设计取舍：
- payload 用文本而非二进制指令表 → **原作者 CSV 脚本零转换**，解析器照搬，轨迹语义不变。
- 帧头+CRC → 抗粘连/丢字节，比裸文本可靠。
- 一帧一命令；单帧最长 240 字节（原版最长命令 REPEAT_LISSAJOUS ≈ 60 字节，余量充足）。

### 3.3 事件帧（EVT，下位机 → 上位机）

`[0xCD][0x01][TYPE 1B][LEN 2B LE][payload 文本][CRC16]`

| TYPE | payload | 触发 |
| --- | --- | --- |
| `0x01` 响应 | `OK ...` / `ERR ...` / `VALUE ...`（沿用原版文本，带 `[L]`/`[R]` 标签） | 每条命令执行后 |
| `0x02` 心跳 | `HB` | **已定：连接期间每秒 1 次**；上位机 3 秒未收到则提示链路异常 |

> 决策已定：心跳开启（1Hz，payload `HB`，极小开销、用于链路健康与静默断连检测）。

### 3.4 CSV 播放时序（上位机）

- 载入：解析原作者 3 列 CSV（`时间ms,左命令,右命令`；空单元格=该侧不动作；第 1 列必须为升序整数 ms；UTF-8/RFC4180 转义）。
- 调度：单调时钟 + 10ms tick；到期事件 → 左列组 `SIDE=0x01` 帧、右列组 `SIDE=0x02` 帧；两帧**同 tick 连续下发**（不等待 ACK，固件非阻塞接收已验证）。
- 暂停/停止 → 下发 `SIDE=0x00 + STOP`；播放结束自动 STOP。
- Seek 跳转（>1.2s）→ 补发两侧最近一条命令（沿用 scripter 的行为，保证姿态连续）。
- 事件间隔 <10ms 时按时间戳排序逐个下发（Burst 由 bleak 队列缓冲；固件 10ms 节拍天然限流）。

## 6. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| Windows BLE 单外设单连接限制 | 仅影响"双连接"旧方案；v2 单连接设计**天然规避** | 单连接内左右复用（帧 SIDE 字段），无此问题 |
| bleak 跨版本 API 差异 | 连接/写回调签名变化 | 锁定 `bleak==0.22.x`；`protocol.py` 与 BLE 调用解耦，适配层集中一处 |
| 脚本事件密集段丢帧/延迟 | 动作卡顿 | 帧 240B 上限 + 不等待 ACK + 固件非阻塞；P4 做 50 事件/秒压力测试；必要时上位机合并 10ms 内相邻事件 |
| CRC/帧解析双端不一致 | 联调困难 | P1 先写**共享测试向量**（同组帧的十六进制样本），两端单测跑同一向量 |
| 轨迹一致性回归 | 改动破坏运动语义 | `DeltaRobot` 只读复用，P4 用 v1 固件做基准对照 |
| GUI 与 BLE 线程竞争 | 界面卡顿/断连 | bleak asyncio 单独事件循环（参考原作者 cdr-player 的线程模型），UI 线程只发信号 |

## 7. 决策点确认结果（已答复）

1. 上位机形态 → **①Python 桌面 GUI（PySide6 + bleak）** ✅
2. 设备名 → **`CDR01v2`** ✅
3. EVT 心跳 → **开启（1Hz `HB`）**（我方决定）✅
4. 视频同步 → **纳入 v1.0 核心**（mpv + vendor libmpv）✅
5. 旧协议 → **完全移除**（旧 App 无法连接）✅
6. 帧 payload 上限 → **240 字节**（原版最长命令 ~60B，余量充足）✅
7. 协议风格 → **二进制帧 + CRC16-CCITT-FALSE**（实现难度低、抗干扰稳定、双端可共享测试向量）✅
8. 补充 → **上位机仿 cdr-player 功能，改用 v2 协议** ✅（连接/手动控制/CSV 播放/视频同步/日志/左右独立）
